### 🔴 F1 [L0 真回归 — 单行修复] static 测试 40 个连环失败,根因钉死
- **现象**: `npm run static:test` → **87 测试 / 46 通过 / 41 失败(47% 失败率)**。
  40 个失败错误同一: `ERR_IMPORT_ATTRIBUTE_MISSING: swordman-attacks.json needs "type: json"`。
- **stale 假说已亲核推翻**: 单独 `node .tmp/test-js/tests/truth/reaction-velocity.test.js` 通过,
  曾疑 results.json stale。但绕过 npm 直跑 `armor/walk-run/replay.test.js` **真 FAIL**(json 在 outDir 仍报错)→ 真回归。
- **根因钉死(grep 全 outDir 的 import 点)**:
  ```
  src/data/manifest/truth/swordman.ts:10876
    export { default as SWORDMAN_ATTACKS } from "./swordman-attacks.json";   ← 缺 with { type: "json" }
  ```
  Node 22 严格 ESM 要求所有 json import 带 attribute。`ReactionResolver.ts:4` 自己带了 attribute(✓),
  但凡经依赖链触达 `swordman.ts` 这行裸 re-export 的测试(40 个,因 import CombatKernel→...→truth/swordman)全部连环挂。
  `reaction-velocity.test.js` 自己直接带 attribute import 且不走该 re-export → 侥幸躲过。
- **为何漏网**: Stage 3 Phase C 加 `swordman.ts` re-export 时,作者给 ReactionResolver 的直接 import 补了
  attribute 却漏了 truth barrel 的 re-export。运行 `static:test` 即可暴露,但 "M7 完成" 声明时**未实跑全量**。
- **修复**: 给 `swordman.ts:10876` 补 ` with { type: "json" }`(单行)。预计 40 测试立即恢复。
- **教训(印证 memory)**: 完美对应 [[feedback-maturity-not-binary]] "声称完成≠实跑全绿" 与
  [[feedback-verify-issue-tracker-against-git-log]]。"76 全绿" 是 snapshot,实测才是真相。
- **状态**: ✅ 根因已亲核钉死(单行)

### 🔴 F3 [测试 bug] QA 测试的按键语义映射错位
- **证据**(`BrowserInputState.ts:49-56`,真实**热键**映射):
  - `KeyX`/`KeyJ` → attack1
  - `KeyZ`/`KeyK` → **UpwardSlash**(测试当成 attack2)
  - `KeyC`/`KeyL` → **jump**(测试当成 attack3)
- **关键校正(审计中 Plan agent 纠错 + 我亲核 `types.ts:6`/`FrameDataAction.ts:130-131`)**:
  attack2/attack3 **是独立 ActionName**,有独立帧数据(attack2=22帧、attack3=31帧),
  可 `requestAction(player,"attack2")` 直接调用。但它们**无独立热键** —— 玩家只能通过
  attack1 连击 chain(`combatCancelTargets`)触达。所以测试想用 `"k"`/`"l"` 单键触发 attack2/3
  是**双重错误**:① 键名格式/语义错(F2+本条) ② 触发模型错(单键≠连击链)。
- **后果**: 即使修正 key 格式,`2.3 Whiff cancel` 期望单键 `k` → `action==="attack2"` 永不成立。
- **根因**: 测试作者(及 manual-qa-checklist.md:34-37)未核游戏真实按键真值表,
  凭 "J/K/L=普攻123" 的直觉假设。违反 CLAUDE.md "禁止臆测" 铁律。
- **状态**: ✅ 已亲核确证(含 attack2/3 独立性校正)

### 🟡 F5 [真值冲突] walk 速度三方打架
- **证据**:
  - 代码 SOT: `LocomotionController.ts:10` `walkSpeed: 2.75` px/tick × 60 = **165 px/s**
    (注释自标 "DNF-like **baseline**" = local_baseline)
  - 测试预期: **121.55 px/s**(moveSpeed=850 PVF 推导)
  - 上个会话实测: **31.63 px/s**
- **三个数无一相同**。31.63 成因**已亲核排除引用失效假说**:`CombatScene.reset()`(:205-206)
  调 `kernel.reset()` **复用同一实例**(不 new),`inputState.clearAll()`(`CombatKernel.ts:126`)
  后引用仍有效。真正成因 = **测试用墙钟 `page.waitForTimeout(2000)` 测 tick-based 物理**:
  headless 下 requestAnimationFrame 被节流,2 秒墙钟实际推进的 tick 数远少于 120 →
  position 增量少 → 速度算偏低。这是**测试方法论缺陷(墙钟 vs tick),不是游戏 bug**。
- **修正方向**: 物理测试必须按 tick 推进 + 读 tick 数归一化,不能用墙钟。佐证 F6。
- **状态**: ✅ 成因已亲核确证(方法论缺陷)
